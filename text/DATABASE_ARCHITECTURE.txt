================================================================================
  資料庫架構 — ฐานข้อมูลออกแบบอย่างไร
================================================================================

ระบบมีข้อมูล 2 ประเภทที่แตกต่างกันมาก จึงออกแบบฐานข้อมูลแยกตามหน้าที่

================================================================================
1. แนวคิดการออกแบบ
================================================================================

ระบบนี้ต้องตอบคำถาม 3 ข้อหลัก:

  คำถามที่ 1: "ใครมีสิทธิ์เข้าห้อง?"        → ตาราง authorized_personnel
  คำถามที่ 2: "ใครเข้าออกห้องเมื่อไหร่?"    → ตาราง room_events
  คำถามที่ 3: "บ่อปลาค่าเซ็นเซอร์เป็นเท่าไหร่?" → ตาราง tank1/2/3

ฐานข้อมูลจึงออกแบบให้ตอบคำถามเหล่านี้ได้อย่างมีประสิทธิภาพ

================================================================================
2. ระบบ Access Control — ออกแบบแบบ Event-Based
================================================================================

แทนที่จะเก็บว่า "ตอนนี้ใครอยู่ในห้อง" (ซึ่งเปลี่ยนแปลงตลอด)
ระบบเลือกเก็บ "เหตุการณ์ที่เกิดขึ้น" แทน

  ─── ตัวอย่างข้อมูลใน room_events ───────────────────────────

  id │ event_type │ person_name │ timestamp
  ───┼────────────┼─────────────┼────────────────────
  1  │ ENTER      │ Tongen      │ 2026-06-03 09:00:00
  2  │ EXIT       │ Tongen      │ 2026-06-03 10:30:00
  3  │ ENTER      │ jiabao      │ 2026-06-03 09:15:00
  4  │ EXIT       │ jiabao      │ 2026-06-03 11:00:00

  ─── วิธีคำนวณจากเหตุการณ์ ──────────────────────────────────

  ระยะเวลาที่อยู่  = EXIT.timestamp − ENTER.timestamp
  ยังอยู่ในห้องไหม = มี ENTER แต่ยังไม่มี EXIT คู่

  ข้อดีของ Event-Based:
  → ไม่ต้อง update ข้อมูลอยู่ตลอดเวลา (เพียงแค่ INSERT)
  → ดูประวัติย้อนหลังได้ครบถ้วน ไม่มีข้อมูลสูญหาย
  → ง่ายต่อการ query รายงาน

================================================================================
3. ปัญหาพิเศษ: State หาย เมื่อ Server Restart
================================================================================

เพราะเก็บแบบ Event-Based → ถ้า server ดับกลางอากาศ
ระบบจะไม่รู้ว่าตอนนี้มีใครอยู่ในห้องบ้าง

  ─── แก้ด้วย room_occupants_log ─────────────────────────────

  ตารางนี้เป็น "snapshot ของ state ปัจจุบัน" มีไว้โดยเฉพาะ

  เมื่อคนเข้า  → INSERT ลงตาราง
  เมื่อคนออก  → DELETE ออกจากตาราง
  Server restart → อ่านตารางนี้ฟื้นฟู state กลับมาทันที

  ─── ตัวอย่าง ────────────────────────────────────────────────

  face_folder │ person_name │ entered_at
  ────────────┼─────────────┼────────────────────
  Std001      │ Tongen      │ 2026-06-03 09:00:00

  ถ้า server restart เวลา 09:30 → ระบบยังรู้ว่า Tongen อยู่ข้างใน

================================================================================
4. ระบบสมาชิก — แยกข้อมูลตัวตนออกจากเหตุการณ์
================================================================================

  authorized_personnel เก็บข้อมูลที่ "ไม่เปลี่ยนบ่อย":
  → ชื่อ, รหัส, บทบาท, เวลาที่อนุญาต, สถานะ

  room_events เก็บข้อมูลที่ "เปลี่ยนทุกวัน":
  → ประวัติการเข้าออกทั้งหมด

  ทั้งสองตารางเชื่อมกันด้วย face_folder (ไม่ใช่ Foreign Key เพราะ
  รูปภาพเก็บเป็นไฟล์ใน disk ไม่ใช่ใน DB)

  ─── ทำไมถึงใช้ face_folder แทน id ─────────────────────────

  face_folder = ชื่อโฟลเดอร์รูปภาพใบหน้าบน disk
  เช่น "Std001", "std002"

  เหตุผล: ระบบ AI ต้องการ path ไปยังรูปภาพโดยตรง
          การใช้ face_folder ทำให้ AI กับ DB ใช้ key เดียวกัน
          ไม่ต้อง query DB ทุกครั้งที่ AI ทำงาน

================================================================================
5. ระบบเซ็นเซอร์บ่อปลา — ออกแบบเป็น Time-Series
================================================================================

ข้อมูลเซ็นเซอร์มีลักษณะเฉพาะ คือ "เกิดขึ้นซ้ำๆ ทุก N วินาที"
เรียกว่า Time-Series Data

  ─── โครงสร้างที่เลือกใช้ ────────────────────────────────────

  แต่ละบ่อมีตารางแยก (tank1, tank2, tank3)
  แต่ละแถว = ค่าเซ็นเซอร์ ณ เวลาหนึ่ง

  Timestamp        │ pH  │ temp │ DO  │ ...
  ─────────────────┼─────┼──────┼─────┼────
  2026-06-03 09:00 │ 7.2 │ 25.8 │ 6.5 │ ...
  2026-06-03 09:05 │ 7.1 │ 25.7 │ 6.6 │ ...
  2026-06-03 09:10 │ 7.3 │ 25.9 │ 6.4 │ ...

  ─── ทำไมถึงแยกตาราง 3 บ่อ แทนที่จะมีคอลัมน์ tank_id ──────

  ทางเลือกที่ 1 (ที่เลือกใช้): แยกตาราง tank1/tank2/tank3
  ทางเลือกที่ 2: ตารางเดียว มีคอลัมน์ tank_id

  เหตุผลที่เลือกแยกตาราง:
  → Query เร็วกว่า ไม่ต้อง filter ทุกครั้ง
  → ง่ายต่อการดูแลแต่ละบ่อแยกกัน
  → ถ้าเพิ่มบ่อใหม่ก็เพิ่มตารางได้เลย ไม่กระทบตารางเดิม

  ─── วิธี Query ที่ใช้บ่อย ───────────────────────────────────

  ดูค่าล่าสุด:
    SELECT * FROM tank1 ORDER BY Timestamp DESC LIMIT 1

  ดูกราฟย้อนหลัง 1 ชั่วโมง:
    SELECT * FROM tank1
    WHERE Timestamp >= DATE_SUB(NOW(), INTERVAL 1 HOUR)
    ORDER BY Timestamp ASC

================================================================================
6. ภาพรวมความสัมพันธ์ทั้งหมด
================================================================================

  [authorized_personnel]
         │
         │ face_folder (ชี้ไปยังโฟลเดอร์รูปใบหน้า)
         │
         ↓
  [faces_db/ บน disk] ← AI อ่านและสร้าง embedding
         │
         │ เมื่อ AI จำหน้าได้
         ↓
  [room_events] ← บันทึก ENTER/EXIT ทุกครั้ง
         │
         │ sync กัน
         ↓
  [room_occupants_log] ← snapshot สถานะปัจจุบัน

  [tank1] [tank2] [tank3] ← ข้อมูลเซ็นเซอร์ แยกอิสระ

  [users] ← บัญชีผู้ใช้เว็บ ไม่เกี่ยวกับ access control

================================================================================
สรุป
================================================================================

  หลักการออกแบบหลัก:
  1. Event-Based: เก็บเหตุการณ์ ไม่เก็บ state → ไม่สูญหาย
  2. State Snapshot: room_occupants_log ช่วยฟื้นฟูหลัง restart
  3. Separation of Concerns: แยกตามหน้าที่ชัดเจน
  4. Time-Series: เซ็นเซอร์แยกตารางต่อบ่อ → query เร็ว
